# Screenshot and Preview Guidance

Screenshots are the primary sales asset. They must communicate the real
product honestly and well.

## What screenshots must communicate

- **Scope** — how much product the buyer gets (views, pages, components).
- **Design quality** — the design system's coherence and personality.
- **Component variety** — the range of states and variants, not one hero shot.
- **Responsive behavior** — mobile/tablet/desktop proof it is real responsive
  work, not a desktop-only mockup.
- **Important interactions** — states that can be shown statically (menus open,
  modals, hover states, forms with content).
- **Unique selling points** — the differentiation (density, a specific
  workflow, a distinctive visual language).

## Honesty rules

- Never misrepresent the product. If a feature is not in the code, it is not
  in a screenshot.
- No fabricated customer logos, testimonials, statistics, awards, or claims.
- Demo data in screenshots uses the same fictional framing as the demo
  ("Example revenue", "Sample customer").

## The screenshot set

Recommended set (adapt to the product):

1. **Hero/overview** — the strongest view of the whole product.
2. **Every primary view** — each page/screen at its intended size.
3. **State close-ups** — a table row menu open, a dropdown, a modal, a form
   with validation, an empty state, a loading state.
4. **Responsive set** — the same key view at mobile, tablet, desktop.
5. **Component gallery** — the kit's components laid out with states labeled.
6. **Detail crops** — typography and spacing detail, showing craft.

## Dimensions and format

- Provide dimensions matching the target marketplace's recommended sizes
  (check and update per marketplace; treat as configurable).
- Caption every screenshot with what it demonstrates.

## Demo video/preview guidance

- If a preview video is planned: show the real demo flow, ~30–60s, no fake
  metrics, no misleading cuts. Show navigation, a real interaction, and a
  mobile pass.

## Image-generation prompts

If image-generation prompts are written to mock up a screenshot:

- Describe visual concepts that accurately represent the actual product (its
  real layout, palette, and typography).
- Explicitly note fictional demo data used.
- Never describe a product with features the code does not have.

## Documentation Screenshots

When documenting HTML documentation, include:

1. **Documentation landing page** — shows the structure and navigation
2. **Component reference page** — demonstrates the documentation format
3. **Code example screenshot** — shows syntax highlighting and formatting
4. **Responsive documentation** — how docs look on mobile/tablet

**Documentation Screenshot Guidelines:**
- Show the actual HTML output, not markdown source
- Include navigation elements
- Demonstrate code block styling
- Show responsive behavior of documentation itself

## Sign-off

Every screenshot is verifiable against the shipped product. If a screenshot
shows anything not in the code, fix the screenshot or the code — one or the
other.
